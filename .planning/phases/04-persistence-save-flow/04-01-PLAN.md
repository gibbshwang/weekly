<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> POST /api/sessions | Untrusted session data crosses from browser to server |
| Client -> DELETE /api/account | Authenticated deletion request crosses from browser to server |
| Firebase ID Token | Bearer token from client must be verified server-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Spoofing | POST /api/sessions | mitigate | Verify Firebase ID token via `adminAuth.verifyIdToken(token)` before any write |
| T-04-02 | Tampering | POST /api/sessions body | mitigate | Write `userId` from verified token (not from request body); validate sessionId and analysisResult presence |
| T-04-03 | Elevation of Privilege | Firestore direct client write | mitigate | All saves go through Admin SDK server route; firestore.rules deny client writes; allow create only if `request.auth.uid == request.resource.data.userId` |
| T-04-04 | Information Disclosure | Orphaned Firestore data | mitigate | DELETE /api/account batch-deletes all sessions BEFORE `adminAuth.deleteUser`; if batch fails, abort deletion entirely (return 500) |
| T-04-05 | Repudiation | PIPA consent bypass | mitigate | `pipaConsentedAt` timestamp stored in Firestore document; SaveConsentDialog is a required UI gate (Plan 02) |
| T-04-06 | Denial of Service | Excessive session saves | accept | Low risk: each save requires valid Firebase auth + Google link; anonymous users cannot save; rate limiting deferred to v2 |
</threat_model>
